## Deskripsi

Konsep analisis dan spesifikasi kebutuhan perangkat lunak. Mahasiswa mempelajari tahapan analisis dan menyusunnya menjadi dokumen kebutuhan yang lengkap dan terstruktur. Menggunakan PBL dengan framework CDIO sebagai cornerstone project.

## Tujuan Pembelajaran

1. Menjelaskan dasar analisis & rekayasa kebutuhan.
2. Menjelaskan stakeholder.
3. Menjelaskan business roles.
4. Menjelaskan tipe-tipe rekayasa kebutuhan.
5. Menjelaskan vision & scope.
6. Menjelaskan elicitation & elicitation indirect.
7. Menyajikan hasil analisis rekayasa kebutuhan.
8. Menyajikan hasil analisis dalam bentuk dokumentasi.

### Luaran

| Luaran                 | Deskripsi                                     |
| ---------------------- | --------------------------------------------- |

| Presentasi progres     | ATS & AAS dengan tanya jawab lisan            |

### Struktur SRS

Mengikuti IEEE 830:

| Bagian                   | Isi                                              |
| ------------------------ | ------------------------------------------------ |
| 1. Introduction          | Tujuan, ruang lingkup, definisi, referensi       |
| 2. Overall Description   | Perspektif produk, fungsi, user classes, batasan |
| 3. Specific Requirements | Functional, non-functional, external interface   |
| 4. Appendices            | Diagram, mockup, glosarium                       |

### Checklist Luaran Minimum

-   [ ] Dokumen Vision & Scope final
-   [ ] Laporan hasil elicitation (wawancara/observasi/workshop)
-   [ ] Daftar stakeholder beserta peran
-   [ ] Minimal 10 functional requirements
-   [ ] Minimal 5 non-functional requirements
-   [ ] Diagram use case atau activity
-   [ ] Mockup UI dasar
-   [ ] SRS final sesuai template dosen

### Bentuk Asesmen

**ATS** — ujian lisan presentasi progres + tanya jawab + daring. Fokus materi pertemuan 1–7 (fondasi analisis & RE). Dinilai dari kejelasan presentasi, kemampuan menjawab, dan kualitas Vision & Scope.

**AAS** — ujian lisan presentasi progres + tanya jawab + daring. Fokus materi pertemuan 8–14 (elicitation, requirement analysis, dokumentasi). Dinilai dari kelengkapan SRS, ketepatan analisis, dan kualitas presentasi akhir.

Beberapa mata kuliah di TRPL menerapkan kebijakan nilai 0 pada komponen apapun = nilai akhir E. Cek kebijakan dosen pengampu di pertemuan pertama.

## Requirement yang Baik

Spesifik, terukur, dapat diverifikasi, tidak ambigu.

| Buruk                 | Baik                                                           |
| --------------------- | -------------------------------------------------------------- |
| "Sistem harus cepat." | "Halaman produk dimuat dalam `<2 detik` pada koneksi 4G."        |
| "UI harus bagus."     | "UI mengikuti panduan Material Design 3."                      |
| "User bisa login."    | "User login dengan email + password; password di-hash bcrypt." |
| "Data harus aman."    | "Data pribadi dienkripsi AES-256 saat transit dan at-rest."    |
