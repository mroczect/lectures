# Minggu 1: Introduction to Requirement Engineering

**Mata Kuliah:** RPL104 — Analisis dan Spesifikasi Kebutuhan Perangkat Lunak
**Pengajar:** Supardianto, M.Eng.

## Capaian Pembelajaran

Setelah pertemuan ini, mahasiswa mampu:

1. Menjelaskan dasar analisis dan rekayasa kebutuhan.
2. Menjelaskan stakeholder dan business roles.
3. Menjelaskan tipe-tipe rekayasa kebutuhan serta Vision & Scope.
4. Menjelaskan elicitation dan elicitation indirect.
5. Menyajikan hasil analisis dan rekayasa kebutuhan dalam bentuk dokumentasi.

## 1. Apa itu Requirement?

Requirement adalah spesifikasi tentang apa yang harus diimplementasikan. Meliputi tiga aspek:

| Aspek           | Penjelasan                                                |
| --------------- | --------------------------------------------------------- |
| **Behavior**    | Bagaimana sistem berperilaku — fungsi, respons, workflow. |
| **Properties**  | Atribut sistem — performa, keamanan, usability.           |
| **Constraints** | Batasan proses — waktu, budget, teknologi, regulasi.      |

Software harus dibuat dengan mempertimbangkan tujuan dan kebutuhan pengguna, bukan asumsi developer.

### Biaya Perbaikan Bug

Semakin awal masalah ditemukan, semakin murah biaya perbaikannya.

| Tahap ditemukan | Biaya relatif |
| --------------- | :-----------: |
| Requirements    |      1×       |
| Design          |      3×       |
| Code            |      5×       |
| Test            |      10×      |
| Production      |     100×      |

Bug di production 100× lebih mahal diperbaiki dibanding yang ditemukan di tahap requirements.

### Contoh Kegagalan Requirement

| Proyek          | Tahun | Masalah                                       | Kerugian        |
| --------------- | :---: | --------------------------------------------- | --------------- |
| Taurus Software | 1993  | Requirement tidak diverifikasi dengan baik    | £3.5 juta       |
| Ariane 5 Rocket | 1996  | Reuse requirement tanpa analisis konteks baru | $370 juta       |
| Denver Airport  | 1994  | Requirement baggage system salah              | $560 juta delay |
| Healthcare.gov  | 2013  | Requirement scaling tidak diprediksi          | Ratusan juta    |

## 2. Masalah Umum dalam Proyek Software

| Masalah                           | Gejala                                                            | Dampak                                |
| --------------------------------- | ----------------------------------------------------------------- | ------------------------------------- |
| **Insufficient user involvement** | Stakeholder hanya dihubungi di awal & akhir; tidak ada demo rutin | Fitur tidak sesuai kebutuhan → rework |
| **Creeping user requirements**    | Scope membengkak tanpa penyesuaian waktu/biaya                    | Deadline meleset, tim burnout         |
| **Ambiguous requirement**         | Setiap pihak punya interpretasi berbeda                           | Developer salah implementasi          |
| **Gold plating**                  | Developer menambah fitur tanpa diminta                            | Waktu & biaya terbuang                |
| **Minimal specification**         | Dokumen requirement terlalu tipis, tidak ada non-functional       | Banyak perubahan di tengah            |
| **Overlooked user classes**       | Sebagian kelas pengguna terlupakan                                | Kebutuhan mereka tidak terpenuhi      |

### Contoh Kebutuhan Ambigu

| Kalimat              | Interpretasi developer | Interpretasi user               |
| -------------------- | ---------------------- | ------------------------------- |
| "Sistem harus cepat" | Response `<100ms`        | Bisa dibuka sebelum ngopi habis |
| "UI harus modern"    | Dark mode + gradient   | Bersih, minimalis, ada search   |
| "Data harus aman"    | HTTPS + bcrypt         | Backup harian + audit log       |

Requirement harus **measurable** dan **testable**.

### Contoh User Classes — Sistem Akademik

| User      | Kebutuhan                |
| --------- | ------------------------ |
| Mahasiswa | Lihat KRS, nilai, jadwal |
| Dosen     | Input nilai, absensi     |
| Admin     | Kelola user, laporan     |
| Orang tua | Lihat nilai anak         |
| Guest     | Info publik kampus       |

Jika orang tua tidak dimasukkan sebagai user class, fitur view nilai anak tidak akan ada.

## 3. Product vs Project Requirement

**Product Requirement** — kebutuhan dari sistem/produk yang dibangun.

**Project Requirement** — kebutuhan di luar produk, terkait proyeknya.

| Product Requirement              | Project Requirement                   |
| -------------------------------- | ------------------------------------- |
| "User bisa login dengan Google." | "Server production di AWS region SG." |
| "Report bisa di-export PDF."     | "Tim lulus training security Q1."     |
| "Aplikasi support mobile."       | "Legal review GDPR compliance."       |

## 4. Proses Rekayasa Kebutuhan

Dua pendekatan utama:

### Well Established (Volere)

Proses mapan dan terstruktur. Alur: project initiation → feasibility study → requirement elicitation → specification → validation → baseline SRS → handover ke developer.

Tantangan:

-   Waktu pengiriman terasa terlalu lama.
-   Sulit membuat prototipe awal.
-   Kolaborasi antar tim menjadi tantangan.
-   Requirement sering berubah, tapi prosesnya kaku.

### Agile

Proses fleksibel dan iteratif. Siklus: backlog → sprint planning → development → review & demo → retrospective → kembali ke backlog.

Tantangan:

-   Pekerjaan berulang (repetitive works).
-   Pelanggan bisa tidak aktif/kooperatif.
-   Dokumentasi informal (kurang detail).
-   Sulit untuk audit & compliance di industri regulated.

### Perbandingan

| Aspek             | Well Established            | Agile                          |
| ----------------- | --------------------------- | ------------------------------ |
| Fokus             | Dokumentasi lengkap di awal | Deliverable inkremental        |
| Perubahan         | Sulit & mahal               | Mudah & natural                |
| Keterlibatan user | Tinggi di awal              | Kontinu setiap sprint          |
| Timeline          | Panjang & terprediksi       | Iteratif & adaptif             |
| Cocok untuk       | Regulated, safety-critical  | Startup, web, mobile           |
| Risiko utama      | Requirement usang           | Scope creep, dokumentasi minim |
