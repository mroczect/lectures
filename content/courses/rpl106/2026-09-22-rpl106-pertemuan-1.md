Setelah pertemuan ini, mahasiswa mampu:

2. Menjelaskan alasan DBMS menggantikan file system.

## 1. Konsep Dasar

### 1.1 Data, Basis Data, DBMS

| Istilah                   | Arti                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Data**                  | Nilai mentah yang belum bermakna (angka, teks, gambar).                                                |
| **Informasi**             | Data yang sudah diolah dan bermakna.                                                                   |
| **Basis Data (Database)** | Kumpulan data yang saling berhubungan dan terorganisir.                                                |
| **DBMS**                  | Software yang mengelola basis data: menyimpan, mengambil, mengubah, mengamankan, dan mengontrol akses. |
| **Sistem Basis Data**     | Gabungan basis data + DBMS + aplikasi + pengguna.                                                      |

Contoh DBMS: MySQL, PostgreSQL, Oracle, SQL Server, SQLite, MongoDB.

**Datum → Data → Informasi**:

- Datum: `"Budi"`
- Data: `("Budi", 25, "Bandung")`
- Informasi: _"Budi, 25 tahun, dari Bandung"_

### 1.2 Peran Basis Data di Aplikasi Nyata

| Aplikasi     | Basis Data dipakai untuk                |
| ------------ | --------------------------------------- |
| Media sosial | User, post, komentar, like, follower    |
| E-commerce   | Produk, pesanan, pembayaran, pengiriman |
| Perbankan    | Nasabah, transaksi, saldo, pinjaman     |
| Peta digital | Jalan, lokasi, rute, titik minat        |
| Rumah sakit  | Pasien, dokter, rekam medis, jadwal     |
| Kampus       | Mahasiswa, dosen, mata kuliah, nilai    |

## 2. Kenapa DBMS, Bukan File System?

Sebelum DBMS, aplikasi menyimpan data di file (TXT, CSV, Excel). Masalahnya:

| Masalah File System                     | Solusi DBMS                             |
| --------------------------------------- | --------------------------------------- |
| Redundansi & inkonsistensi              | Normalisasi + constraint                |
| Sulit akses data (harus tulis program)  | Query language (SQL)                    |
| Isolasi data (format berbeda tiap file) | Skema terpusat                          |
| Masalah integritas                      | Constraint, foreign key, transaksi ACID |
| Konkurensi terbatas                     | Concurrency control                     |
| Keamanan minim                          | Autentikasi + role + privilege          |
| Sulit recovery                          | Log & backup otomatis                   |

**ACID** — empat jaminan transaksi di DBMS:

- **Atomicity** — semua atau tidak sama sekali.
- **Consistency** — data tetap valid.
- **Isolation** — transaksi tidak saling mengganggu.
- **Durability** — data tersimpan permanen setelah commit.

## 3. Model Data

Model data = cara menggambarkan struktur data, relasi, dan constraint.

| Model                        | Deskripsi                            | Dipakai di                |
| ---------------------------- | ------------------------------------ | ------------------------- |
| **Relasional**               | Tabel + relasi antar tabel           | MySQL, PostgreSQL, Oracle |
| **Entity-Relationship (ER)** | Entitas + relasi (untuk perancangan) | Tahap desain              |
| **Semi-terstruktur**         | Data fleksibel (JSON, XML)           | MongoDB, web services     |
| **Object-based**             | Objek + class + inheritance          | OODBMS (jarang)           |
| **Hierarkis / Jaringan**     | Pohon / graf                         | Sistem legacy             |

Yang dominan saat ini: **relasional**. Karena sederhana, matang, dan didukung banyak tools.

## 4. Bahasa Basis Data

| Kategori                             | Fungsi                    | Contoh perintah                   |
| ------------------------------------ | ------------------------- | --------------------------------- |
| **DDL** (Data Definition Language)   | Mendefinisikan skema      | `CREATE TABLE`, `ALTER`, `DROP`   |
| **DML** (Data Manipulation Language) | Mengubah & mengambil data | `INSERT`, `UPDATE`, `DELETE`      |
| **DQL** (Data Query Language)        | Mengambil data            | `SELECT` (sering dimasukkan DML)  |
| **DCL** (Data Control Language)      | Kontrol akses             | `GRANT`, `REVOKE`                 |
| **TCL** (Transaction Control)        | Kelola transaksi          | `COMMIT`, `ROLLBACK`, `SAVEPOINT` |

Contoh skema:

```sql
CREATE TABLE Mahasiswa (
  nim CHAR(10) PRIMARY KEY,
  nama VARCHAR(100),
  angkatan INT
);
```

Contoh query:

```sql
SELECT nama FROM Mahasiswa WHERE angkatan = 2026;
```

## 5. Perancangan Basis Data

Tahapan:

1. **Requirement analysis** — pahami kebutuhan pengguna.
2. **Conceptual design** — model ER: entitas, atribut, relasi.
3. **Logical design** — konversi ER ke skema relasional (tabel, PK, FK).
4. **Schema refinement** — normalisasi untuk kurangi redundansi.
5. **Physical design** — index, storage, tuning.

**Normalisasi** memisahkan data ke tabel sesuai entitas. Tujuannya:

- Menghindari duplikasi.
- Mencegah anomali insert/update/delete.

Contoh sederhana: data penerbangan dan data penumpang dipisah — bukan digabung jadi satu tabel besar.

## 6. Arsitektur Sistem Basis Data

### 6.1 Tiga Level Abstraksi

| Level        | Deskripsi                       | Contoh               |
| ------------ | ------------------------------- | -------------------- |
| **Physical** | Bagaimana data disimpan di disk | Blok, index, page    |
| **Logical**  | Apa data yang disimpan          | Tabel, kolom, relasi |
| **View**     | Bagaimana pengguna melihat      | Report, dashboard    |

DBMS menyembunyikan detail physical dari pengguna — disebut **data abstraction**.

### 6.2 Application Architecture

| Arsitektur     | Deskripsi                           | Contoh                |
| -------------- | ----------------------------------- | --------------------- |
| **Two-tier**   | Aplikasi ↔ DBMS langsung            | Aplikasi desktop lama |
| **Three-tier** | Client ↔ App server ↔ DBMS          | Web aplikasi modern   |
| **N-tier**     | Multi-layer, ada API gateway, cache | Sistem enterprise     |

Aplikasi web modern umumnya three-tier: frontend (React/Vue), backend (Node/Python/Go), DBMS (PostgreSQL/MySQL).

### 6.3 Database Architecture

| Tipe              | Deskripsi                                  |
| ----------------- | ------------------------------------------ |
| **Centralized**   | Satu server, semua klien terhubung ke sana |
| **Client-server** | Server basis data + banyak klien           |
| **Parallel**      | Beberapa CPU/disk untuk kecepatan          |
| **Distributed**   | Data tersebar di beberapa lokasi           |

## 10. Studi Kasus 2 — Flight Data

Modul meminta konversi data penerbangan (Figure 2) jadi 2 tabel.

### 10.1 Tabel Flight

| Attribute      | Data             |
| -------------- | ---------------- |
| Flight_ID      | GA-101           |
| Airline        | Garuda Indonesia |
| Origin         | Jakarta (CGK)    |
| Destination    | Denpasar (DPS)   |
| Departure_Time | 08:30            |
| Arrival_Time   | 11:15            |
| Aircraft_Type  | Boeing 737-800   |

`Flight_ID` = Primary Key.

### 10.2 Tabel Flight Details

| Flight_ID | Passenger_ID | Passenger_Name | Seat | Class    | Ticket_Price |
| --------- | ------------ | -------------- | ---- | -------- | ------------ |
| GA-101    | P001         | Andi Wijaya    | 12A  | Economy  | 1.250.000    |
| GA-101    | P002         | Siti Nurhaliza | 12B  | Economy  | 1.250.000    |
| GA-101    | P003         | Budi Santoso   | 03A  | Business | 3.500.000    |

- `Flight_ID` = FK ke tabel Flight.
- `(Flight_ID, Passenger_ID)` = composite PK.

### 10.3 Kenapa Dipisah?

Kalau digabung, kolom Airline, Origin, Destination, Departure diulang tiap baris penumpang. Kalau jadwal berubah, harus update semua baris → rawan inkonsistensi. Dipisah = update 1 baris saja. Inilah **normalisasi**.

## 12. Ringkasan

1. Data ≠ informasi. Basis data mengorganisir data agar bermakna.
2. DBMS menggantikan file system karena ACID, konkurensi, keamanan, dan skalabilitas.
3. Model relasional (tabel + PK + FK) adalah yang dominan.
4. Bahasa DBMS: DDL, DML, DCL, TCL.
5. Perancangan lewat tahap: requirement → ER → relasional → normalisasi → physical.
6. Arsitektur: tiga level abstraksi (physical, logical, view) + three-tier application.
7. Skill inti: melihat dunia nyata sebagai kumpulan tabel yang saling terhubung.
